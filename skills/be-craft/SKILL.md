# Craft/Yii backend

Load project-local rules through the [`craft_twig_rules` MCP](/Users/joostwaaijer/Documents/workspace/robuust-agents/mcp/craft-twig-rules/README.md): call `find-rules` for known target paths, or `list-rules` for repository-wide work or unknown targets, before acting on them. Reuse unchanged results for already-inspected paths; look up new paths as scope grows. Apply returned rules within their scope, subject to explicit user instructions. Do not read `.ai/rules` directly.

If the MCP is unavailable, report the missing rule access and defer work that requires rules not yet retrieved. Reuse still-current retrieved rules and continue independent authorized work; tool unavailability does not waive the lookup requirement or permit direct rule-file access. For documentation questions, the existing [search CLI](/Users/joostwaaijer/Documents/workspace/robuust-agents/mcp/craft-twig-rules/bin/search-craft-docs.mjs) is a fallback only when its documentation track matches the project's version: `node "<mcp-directory>/bin/search-craft-docs.mjs" --project-root "<project-root>" "<query>"`.

Before version-dependent advice or changes, establish the relevant Craft, Yii, and plugin versions from Composer manifests, lockfiles, and installed package metadata where available. Distinguish declared constraints, locked versions, and the actual installation; report discrepancies affecting the task instead of silently choosing one. Select official documentation for the version used by the target environment, including its prerelease status when relevant. Where documentation covers a whole major release, check API introduction/deprecation notes and the installed source for minor-version compatibility. Do not install or upgrade packages just to discover their versions.

Ground behavior and contract choices in exact issue/specification, wireframe/design or accepted-decision references; current code alone does not settle ambiguous intent. If a material choice remains open, ask the user before dependent implementation and offer direct input or a user-chosen, authorized decision issue for the project manager. Use the standalone [project decision procedure](../../agents/references/project-decisions.md) for reconciliation and escalation; continue independent authorized work.

- Keep application-owned changes at the project’s existing architectural altitude; do not introduce repositories, DTOs, or abstractions without evidence that the project uses them. For defects owned by Craft, Yii, or a plugin, follow the shared [upstream-dependency-fixes](../upstream-dependency-fixes/SKILL.md) workflow before adding project-level fixes.
- Make controller, service, event, queue, and template response contracts explicit and narrow. Use supported Craft request-validation and permission helpers for the agreed access rules. Preserve unrelated response fields/types, status codes, validation and redirects; use the standalone [preservation comparison](../../agents/references/behavior-preservation.md) for affected before/after consumers, including frontend consumers reached by backend changes.
- Query Craft elements deliberately. Identify repeated per-element relation queries and the actual rendering or serialization consumers before changing the loading strategy. Choose the native lazy eager-loading or eager-loading-map APIs supported by the installed version, avoiding unused relation loads and unnecessary changes to working maps. Preserve query filters, ordering, site scope, and consumer expectations for queries versus loaded collections; consult that version's eager-loading documentation for the applicable API question.
- Keep persistent state and authorization on the server.
- When the project uses Craft project config, treat it as a Craft contract. Let Craft generate `config/project/` through the project's supported workflow rather than authoring generated YAML by default. Review the resulting diff for the requested configuration change and ensure its `dateModified` timestamp is updated in the same change set. Separate generation and review from applying config, migrations, or data changes; perform those only within the task's existing authority for the target environment. Consult the installed version's project config documentation before choosing an operation.
- For a concrete Craft CMS, Yii, or plugin API question, search the matching official version's documentation with a targeted query. Use `search-craft-docs` through the `craft_twig_rules` MCP, or its CLI, only when its supported documentation track covers that question and project version. Otherwise use available search/browsing tools to inspect the relevant official Craft, Yii, or plugin documentation directly. If matching documentation is unavailable, use the installed source or release-tagged API definitions as evidence and state the limitation; do not substitute another version's documentation or treat a lookup tool's version restriction as a restriction on this skill. Do not fetch documentation when repository evidence is sufficient.
- Do not fetch Tailwind documentation for backend-only work.

Writing, modifying, deleting or running tests requires explicit user authorization for the objective; follow the shared [Testing and Verification](../../agents/templates/org/AGENTS.md#testing-and-verification) rules. Inspection and permitted non-test checks do not authorize data changes or publication.

For template changes, use [`fe-craft`](../fe-craft/SKILL.md); for Turbo response contracts, use [`hotwired-patterns-craft`](../hotwired-patterns-craft/SKILL.md). Use [`infer-craft-conventions`](../../references/robuust-agents/skills/infer-craft-conventions/SKILL.md) when convention discovery or recording is requested, not as a prerequisite for routine backend edits.
