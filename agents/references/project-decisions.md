# Source-backed project decisions

Use this reference for a material product, interaction, domain, contract or policy choice, including architecture that constrains those outcomes. It is a standalone procedure; reading it does not require agent-team, a plan, delegation or additional approval for already-authorized work. Explicit user instructions and accepted project decisions govern.

## Establish the intended outcome

Inspect the relevant issues and discussions, specifications, wireframes/design states, accepted decisions, existing contracts and actual producers/consumers. Use the source types present; do not require every project to provide all of them. Identify exact source locations and explain how they support each consequential choice.

Distinguish confirmed requirements, observed implementation, inference, proposals and open questions. Choose authority by the concern and accepted decisions, not tool ranking or timestamp alone. Existing code establishes current behavior; a preferred pattern, available API, mock value or unspecified state does not settle an ambiguous requested outcome.

Reuse still-applicable decisions. Resolve routine implementation mechanics from project conventions and supported APIs when they preserve the established outcome and contracts; no generic planning or approval round is needed.

## Resolve a material gap

When sources are missing, conflicting or support materially different outcomes without selecting one, explain the inspected evidence, missing choice and practical implications. Ask the user before dependent implementation, assertions or acceptance. Keep recommendations labeled as proposals; an unanswered question, elapsed time or an implementation request is not the missing decision. Continue independent authorized work.

Offer direct input or a decision issue for the project manager in the existing tracker. When already delegated, return the gap to the existing coordinator for consolidation; this does not require creating a team or coordinator for standalone work.

## Create a decision issue only when chosen

Prepare the concrete question, exact source links and their limits, meaningful alternatives and implications, affected criteria/contracts and blocked work. Check for an existing issue owning that decision and follow the project's routing conventions. Do not invent a project, project-manager identity or assignment.

Publish or update the issue only within actual user authorization. A request to create that scoped issue authorizes its tracker write without another generic confirmation; it does not authorize a separate message to the project manager. Ask only for missing routing details that are necessary, and prepare a draft while they remain pending.

Link the unresolved dependency from the existing requirement, roadmap or task state within its authorized write scope. Creating, assigning or closing an issue is not the decision. Keep dependent work pending until explicit user input or an accepted authoritative project decision resolves it. Record the answer, source and effect on the contract/criteria in their existing owner before continuing; independent work can remain partly ready.
